# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Single Terraform module (root module, no submodules) that provisions an `aws_kinesis_firehose_delivery_stream` plus all supporting resources (IAM roles/policies, CloudWatch log groups/streams, security groups). It supports every Firehose source and destination through one set of root-level `.tf` files — there is no per-destination submodule split.

Published to the Terraform Registry as `fdmsantos/kinesis-firehose/aws`. Versioning is automated via semantic-release based on Conventional Commits (see `.releaserc.json`); `CHANGELOG.md` and version bumps are generated by CI, never hand-edited.

## Commands

- `pre-commit run -a` — runs `terraform fmt`, `terraform validate`, `terraform-docs`, and `tflint` (scoped rules, see `.pre-commit-config.yaml`). Run this before committing any `.tf` change; CI (`.github/workflows/pre-commit.yml`) runs it against both the min and max supported Terraform versions.
- `gh-md-toc README.md` (via `make generate-toc`) — regenerates the README table of contents after adding/removing a `##`/`###` section.
- `terraform-docs` regenerates the Requirements/Providers/Modules/Resources/Inputs/Outputs tables embedded in `README.md` — run it (via pre-commit) whenever `variables.tf`, `outputs.tf`, or provider/resource declarations change, and don't hand-edit those generated tables.
- No test suite in this repo; validation is `terraform validate` + `tflint` + manual testing via the examples under `examples/`.
- To exercise a change end-to-end, `cd examples/<destination>` (e.g. `examples/s3`, `examples/redshift`, `examples/snowflake`, `examples/opensearch`, `examples/http-endpoint`, `examples/splunk`, `examples/iceberg`) and run standard `terraform init/plan/apply` there against real AWS credentials.

## Architecture

All logic lives in five root files that are read together, not independently:

- **`variables.tf`** (~200 inputs) — every knob for every source/destination/feature, flat namespace with prefixes per concern (`s3_backup_*`, `vpc_*`, `data_format_conversion_*`, etc.).
- **`locals.tf`** — the real control plane. It normalizes `var.destination` (an alias like `datadog`, `coralogix`, `honeycomb`, ... all map through `local.destinations` to the underlying Firehose destination type, e.g. `http_endpoint`) into `local.destination`, and derives booleans (`is_kinesis_source`, `is_search_destination`, `enable_processing`, `s3_destination`, VPC/security-group flags, etc.) that `main.tf` and `iam.tf` branch on. When adding a feature, the derivation almost always belongs here, not inline in `main.tf`.
- **`main.tf`** — the single `aws_kinesis_firehose_delivery_stream` resource. Every source and destination is a `dynamic` block gated by a `local.*` flag or `local.destination == "..."` check (e.g. `dynamic "extended_s3_configuration"`, `dynamic "redshift_configuration"`, `dynamic "http_endpoint_configuration"`), so all destinations coexist in one resource and only one branch is ever populated per apply. Processing steps (Lambda transform, dynamic partitioning, CloudWatch decompression, delimiter/deaggregation) are assembled into `local.processors` as an ordered list and rendered through a shared `dynamic "processors"` block reused across S3/Redshift/Splunk/etc. Also holds the security groups and CloudWatch log groups/streams for the destination and backup logging.
- **`iam.tf`** — one `aws_iam_role` for Firehose (conditionally created via `var.create_role`) plus one `aws_iam_policy_document`/`aws_iam_policy`/`aws_iam_role_policy_attachment` triplet per capability (kinesis source, MSK source, Lambda, S3, S3 KMS, SSE KMS, Glue, CloudWatch, Redshift, Elasticsearch/OpenSearch/OpenSearch Serverless incl. cross-account and service-linked roles, VPC, Iceberg, Secrets Manager, application role for direct-put). Each triplet is gated by the same `local.*`/`var.*` flags used in `main.tf` — when a destination or feature is added there, its IAM permissions go here following the existing triplet pattern.
- **`outputs.tf`** — thin passthrough of created resource attributes.

### Adding support for a new destination or feature

1. Add its variables to `variables.tf` (prefixed by destination/feature name).
2. Add any derived flags/values to `locals.tf`, and if it's a destination alias, add it to `local.destinations`.
3. Add the corresponding `dynamic` block(s) in `main.tf`, following the pattern of an existing similar destination.
4. Add the IAM policy document/policy/attachment triplet in `iam.tf` if it needs permissions.
5. Add outputs if relevant, add an example under `examples/`, and update the relevant `README.md` sections (features list, "How to Use", destinations mapping table) — then run `terraform-docs`/pre-commit to regenerate the generated tables.

### Module versioning constraint

AWS provider version is pinned per module major version (see README "Module versioning rule"): module `>=3.x.x` requires `aws` provider `>= 5.33` (currently `>= 5.73, < 7.0` per `versions.tf`). Don't use provider features outside that range without bumping the constraint deliberately.
